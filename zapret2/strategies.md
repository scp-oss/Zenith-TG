# Кандидаты `--lua-desync=` для TG_MTPROTO

**Синтаксис имён операторов ниже не подтверждён против конкретной сборки
nfqws2 на целевом боксе** (см. предупреждение в `TG_MTPROTO.block.conf`)
-- это список ГИПОТЕЗ, обоснованных публично известными техниками обхода
DPI-блокировки Telegram, а не проверенный рецепт. Перед первым прогоном
`rank_strategies.sh` по этому профилю: свериться с реальными
`strategy=N`, уже работающими в `/opt/zapret2/config` на конкретном
сервере -- какие операторы там реально используются и как называются.

## Почему вообще эти техники, а не TLS-специфичные (`hostfakesplit`,
## `tls_client_hello_clone`)

Обфусцированный MTProto -- НЕ TLS. У init-пакета (см. `prober/proto.py`)
нет ClientHello, нет SNI, нет никакого распознаваемого поля с именем
хоста внутри полезной нагрузки -- только 64 байта, специально
сконструированные похожими на случайный шум (это и есть сама
маскировка протокола). Все TLS-контентно-осведомлённые операторы этого
проекта (сплит по позиции `--filter-l7=tls`-заголовка/SNI-маркера)
здесь неприменимы буквально -- делить нечего, никакого "midhost"/
"midsld"-подобного маркера в потоке нет. Нужны операторы, работающие на
уровне TCP-сегментации/таймингов, а не содержимого.

## Кандидаты (в порядке предполагаемого приоритета для первого прохода)

1. **`fake` (decoy-пакет перед реальным init)** -- отправить один
   "поддельный" TCP-сегмент с намеренно неверными данными непосредственно
   перед настоящим init-пакетом. Классическая техника: примитивная DPI,
   которая инспектирует только ПЕРВЫЙ увиденный сегмент потока, ловит
   decoy вместо реального init и либо пропускает поток как
   "не Telegram", либо десинхронизирует свой tracked seqnum относительно
   того, что реально видит сервер.

2. **`fake` с заниженным TTL** -- то же самое, но decoy-пакет собран с
   TTL, рассчитанным так, чтобы дойти до предполагаемого DPI-узла (обычно
   близко к клиенту у российских ISP), но не дойти до настоящего DC
   Telegram. DPI видит decoy и принимает решение по нему; реальный
   сервер decoy вообще не получает. Требует знания примерного
   количества хопов до DPI-узла на конкретной сети -- то, что
   подбирается эмпирически через перебор strategy=N (см. п. "Численный
   диапазон TTL" ниже), не задаётся заранее.

3. **Сегментация init-пакета на границе байт (не по содержимому)** --
   разбить настоящий 64-байтный init на 2+ TCP-сегмента в ЯВНО заданных
   байтовых позициях (напр. после байта 8 -- граница
   `SKIP_LEN`/начала ключевого материала в `proto.py`, где статистическая
   "форма" данных меняется). Смысл тот же, что у `hostfakesplit` для TLS,
   но по фиксированной позиции, а не по контентному маркеру -- многие DPI
   реализации фингерпринтят именно ПЕРВЫЙ сегмент целиком, разбивка сразу
   меняет то, что видно в нём.

4. **`disorder`-подобная техника (сегменты не по порядку)** -- отправить
   вторую часть init раньше первой (сервер TCP-стеком всё равно соберёт
   правильно per RFC, простая пассивная DPI, читающая поток линейно по
   мере прибытия сегментов, может собрать неправильно или не собрать
   вовсе).

5. **Комбинация fake + сегментация** -- по опыту оригинального zapret
   (см. `docs`/примеры конфигов bol-van/zapret для Telegram в его же
   репозитории) комбинация обычно эффективнее одиночных техник по
   отдельности -- decoy сбивает первичное распознавание, сегментация не
   даёт восстановить сигнатуру даже если DPI decoy проигнорировала.

## Численный диапазон TTL (если оператор `fake:ttl=` реально существует
## в этой сборке)

Начинать перебор с TTL 3-8 (типичное число хопов от домашнего/офисного
клиента до пограничного DPI-узла провокатора в РФ по опубликованным
измерениям на других профилях этого же проекта, см. `netcheck.sh`/
`z2r_autobench_lib.sh`, если там уже есть аналогичная логика для других
TCP-профилей -- имеет смысл переиспользовать тот же диапазон, не
изобретать заново).

## Что НЕ будет работать наверняка (сразу exclude)

- Любой TLS-content-aware оператор (`hostfakesplit`, `tls_client_hello_*`)
  -- нет контента, который они ищут.
- `circular_locked:key=N:proto=udp:...` -- это UDP-примитив (см.
  VOICE_UDP в основном проекте), Telegram Desktop по умолчанию для
  MTProto использует TCP, не UDP (в отличие от голосовых звонков,
  которые здесь не рассматриваются -- отдельная, ещё не покрытая
  задача, ближе по духу к VOICE_UDP, чем к TG_MTPROTO).
