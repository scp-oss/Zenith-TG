# Zenith-TG

Модуль прозрачного DPI-обхода Telegram для экосистемы
[z2r_autobench](https://github.com/scp-oss/z2r_autobench)/[zapret2](https://github.com/bol-van/zapret2).

## Зачем отдельный модуль, а не `tg-ws-proxy`

Рассматривался [Flowseal/tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy)
-- рабочий, живой проект, но другая модель: локальный MTProto-прокси,
который нужно вручную (или по `tg://`-ссылке) прописать в настройках
Telegram на КАЖДОМ устройстве. Это ломает главное свойство остальной
экосистемы z2r_autobench -- **прозрачность**: zapret2/nfqws2 перехватывает
и манглит пакеты на уровне ядра для ЛЮБОГО приложения на устройствах за
роутером/сервером, ничего не требуя от клиента. `tg-ws-proxy` -- по сути
подмена транспорта (MTProto поверх WebSocket до настоящих доменов
Telegram), а не обход DPI на уровне пакетов.

Zenith-TG идёт другим путём: **тот же трюк, что и для YouTube/Discord/RKN-
профилей** -- `--lua-desync=` стратегии nfqws2, применённые к настоящему,
никак не изменённому MTProto-трафику Telegram Desktop. Ноль настройки на
стороне клиента.

## Почему это отдельный компонент, а не просто ещё один профиль в
## `PROFILE_NUMBERS`

Telegram MTProto (обфусцированный транспорт) -- **не TLS и не HTTP**: нет
ClientHello, нет SNI, нет доменного имени в трафике вообще, только TCP к
известным IP-диапазонам Telegram DC. Это значит:

- Матчится через `--ipset=` (IP-диапазоны), а не `--hostlist=` (домены) --
  единственный профиль в экосистеме с таким гейтом.
- Существующий тестер (`probe_url`/`probe_http_url` в
  `z2r_autobench_lib.sh`, curl + подсчёт байт ≥`MIN_BYTES_THRESHOLD`) тут
  физически неприменим -- Telegram DC не отдаёт HTTP-контент по этому
  порту. Нужен протокол-осведомлённый пробер -- см. `prober/`.

## Состав

```
prober/
  proto.py            -- независимая реализация init-пакета
                          obfuscated-транспорта MTProto (публичный
                          протокол, сверена с рабочим кодом tg-ws-proxy,
                          но не скопирована -- своя задача)
  mtproto_probe.py     -- CLI: шлёт init-пакет на реальный DC, отличает
                          "DPI оборвала соединение" от "сервер получил
                          мусорный ключ и молча ждёт" по ВРЕМЕНИ разрыва,
                          не по содержимому ответа
cidr/
  fetch_telegram_cidr.sh  -- тянет официальный список подсетей Telegram
                             (core.telegram.org/resources/cidr.txt)
  telegram_ipv4.txt       -- снапшот, регенерируется скриптом выше
zapret2/
  TG_MTPROTO.block.conf   -- ЧЕРНОВИК блока конфига (--filter-tcp/
                             --ipset/--payload=unknown + кандидаты
                             --lua-desync=) -- ТРЕБУЕТ живой проверки,
                             см. предупреждение в самом файле
  strategies.md           -- обоснование кандидатов, что НЕ будет
                             работать заведомо
tests/
  test_proto.py            -- детерминированные тесты (без сети):
                              round-trip расшифровки, избегание
                              зарезервированных байт
```

## Быстрый старт (диагностика, без применения стратегий)

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

# Обновить список подсетей Telegram
bash cidr/fetch_telegram_cidr.sh

# Живой зонд: доходит ли init-пакет MTProto до всех 5 основных DC СЕЙЧАС
# (без активной стратегии -- baseline)
.venv/bin/python3 prober/mtproto_probe.py --repeat 3

# Тесты (без сети)
.venv/bin/python3 tests/test_proto.py
```

Если baseline уже показывает `FAIL` (разрыв в первые миллисекунды) на
всех DC -- DPI блокирует безусловно, есть за что бороться, есть смысл
пробовать `zapret2/TG_MTPROTO.block.conf`. Если baseline уже `OK` --
блокировки нет (или она уже не активна на этой сети), применять
стратегии незачем.

## Что ТРЕБУЕТ живой проверки перед боевым использованием

У этой разработки не было исполнительного доступа к целевому
zapret2-серверу (типичное ограничение всей этой экосистемы, см.
`z2r_autobench/CLAUDE.md` -- "No execution access to the deployment box
itself"), поэтому:

1. **`--ipset=` флаг** -- имя и формат нужно свериться с `nfqws2 --help`
   на конкретной сборке (ожидается плоский текстовый файл, один CIDR на
   строку, по прецеденту оригинального zapret -- но не проверено на
   z2r-форке).
2. **Имена `--lua-desync=` операторов** в `TG_MTPROTO.block.conf`
   (`fake`, `multisplit`, ...) -- ГИПОТЕЗЫ, не подтверждённый синтаксис
   этой сборки. См. `zapret2/strategies.md`.
3. **`mtproto_probe.py`** протестирован живьём против настоящих DC
   Telegram (149.154.x.x, DC1-5) -- TCP доходит, init-пакет расшифровывается
   корректно (round-trip тест в `tests/test_proto.py`), соединение ведёт
   себя как ожидается от реального сервера. Это подтверждает, что зонд
   работает технически корректно -- НЕ подтверждает, работает ли обход
   DPI (для этого нужен целевой сервер за реальной блокировкой).

## Интеграция в z2r_autobench (когда стратегия найдётся и подтвердится)

Не выполнялась в рамках этого модуля (сознательно отдельный репозиторий).
Когда рабочая стратегия для `TG_MTPROTO.block.conf` будет подтверждена
вживую:

1. Вписать блок в `/opt/zapret2/config` (вручную или через
   `promote_apply_cli.sh` -- формат `TG_MTPROTO.block.conf` уже совместим
   с её HEADER-режимом).
2. Добавить профиль в `autotune_daemon.sh`: `PROFILE_TITLE[10]="TG_MTPROTO"`,
   `PROFILE_PROTO[10]="tcp"`, номер профиля -- следующий свободный после
   текущего максимума (см. `README.md` z2r_autobench "Профили" на момент
   интеграции, сейчас максимум -- 9).
3. Тестер для `rank_strategies.sh` нужен отдельный (не
   `probe_url`/`probe_http_url`) -- обёртка вокруг `mtproto_probe.py` по
   тому же контракту, что уже есть у `quic_probe.py` для профиля 5
   (YT_QUIC_UDP): печатает результат в parseable виде, код возврата
   0/1.
4. Пункт меню в `z0r` (`12`-подобный, "Zapret сервис") НЕ трогать --
   TG_MTPROTO живёт ВНУТРИ того же `/opt/zapret2/config`, не отдельный
   systemd-юнит (в отличие от `tg-ws-proxy`, у этого нет собственного
   процесса).
